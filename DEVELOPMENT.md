# Development handoff

## Goal and scope

Build remote co-op for two players sharing control of one ship in Void War. The long-term requirement is for the guest to issue crew orders through the same native interaction used in single-player. The original guest panel validated host-side command handling and state sync. The guest ship view mirrors host snapshots and accepts single-player mouse gestures for one shared crew member.

The current target is the full Windows Steam game, build `26906873`, with a copy of the game on each PC. Steam networking was the first choice. Direct IP was the agreed fallback if Steam failed the remote connection test. That test passed, so the project uses Steam. Keep original game data, patched binaries, and extracted game assets out of Git. Build and install from each player's own copy using the [README](README.md#build).

## Architecture and game integration

- [New-ProbeData.ps1](New-ProbeData.ps1) pins the vanilla input by SHA-256, runs UndertaleModTool CLI 0.9.2.0, and publishes a new output without overwriting an existing file. [ApplyProbe.csx](probe/ApplyProbe.csx) compiles the GML, registers two Steam extension functions the compiler otherwise treats as variables, and installs a guarded creation hook in `rmMainMenu`. The persistent probe is intended to carry the connection through room changes without spawning a duplicate on return to the menu.
- [Create.gml](probe/Create.gml) and [Step.gml](probe/Step.gml) handle Steam IDs, the in-game editor, and the two-peer session. IDs are parsed digit by digit as 64-bit integers. The peer's Steam ID, packet bounds, magic, game build, and protocol version are checked. Ping/pong measures RTT and detects loss of replies. **F10** closes the local session. [Cleanup.gml](probe/Cleanup.gml) also frees the buffers when the probe is destroyed.
- [CrewTest.gml](probe/CrewTest.gml) uses probe protocol **4**. The 15-byte header still carries magic, build, protocol, packet kind, and sequence. Per-share layout packets carry room bounds, native tile positions, and sprite names. The host retries layout until the guest acknowledges that share generation. Separate 31-byte updates every 250 ms carry the crew position, target tile, arrival, and order acknowledgement. The guest retries its pending numbered order until a snapshot acknowledges it or a newer click replaces it. The host uses the sharing token to reject orders for an old selection and sequence numbers to avoid applying duplicates. Room numbers refer to cells in the host's map of up to 24 rooms. GameMaker instance IDs stay on the host.
- The native room-click path in `oCell` Step calls `crew_move_set_target` from `scrCrewMovement` for ordinary room movement. The host uses that function for guest orders after checking the live crew, hull, and destination. `currentCellID` is the reserved destination and can change before physical arrival. The snapshot uses `collidingCellID` while moving and `crew_has_reached_destination` to report arrival. The host runs the encounter. The last valid order processed by the host wins, whether it came from the host or the guest. The playtest confirmed this behavior and the user approved it. The numbered guest panel remains available at the title screen. The optional guest ship view uses the same ordered room slots and sends orders to the same host handler.
- [GuestView.gml](probe/GuestView.gml) draws local hull and portrait sprites from host-supplied asset names, room bounds, and crew position. The new guest room is outside the normal room order and contains no combat instances. The guest selects the crew marker with a left-click and right-clicks the nearest native tile within a room. The host validates the tile and calls the native precision move for a vacant tile or the native occupied-tile fallback. The numbered panel still sends ordinary room orders. Both clicks use the same coordinate transform as drawing. The custom view covers one shared crew member with single-player mouse gestures.

References for build-specific work include the [Void War developer FAQ](https://steamcommunity.com/app/2853590/discussions/0/4695658570140629717/), [UndertaleModTool 0.9.2.0](https://github.com/UnderminersTeam/UndertaleModTool/releases/tag/0.9.2.0), [GameMaker instance persistence](https://manual.gamemaker.io/lts/en/GameMaker_Language/GML_Reference/Asset_Management/Instances/Instance_Variables/persistent.htm), and [Valve's legacy P2P API reference](https://partner.steamgames.com/doc/api/ISteamNetworking). Valve deprecates that API. It is the one available through Void War's bundled GameMaker extension and used in the successful connection playtest.

## Technical history and known issues

- `b3efb45` fixed the old native dialog crash. UndertaleModTool compiled `async_load[? "id"]` as array indexing and tried to convert `"id"` to an integer. Explicit map lookups worked in the runner. `5bb993f` then removed the native dialog because returning from Alt-Tab in fullscreen made it minimize whenever the player interacted with it. The in-game editor keeps its own draft across focus changes.
- `8b484ba` fixed a receive crash caused by `steam_net_packet_get_size` compiling as a variable read. `steam_net_close_p2p_session` had the same problem. Register both using their bundled extension declarations before compiling and verify direct calls. Both ran in Steam.
- With a mismatched version, the peer that detects the mismatch closes the session immediately. Two-PC testers saw a mismatch on one side and **No reply** on the other. This is a reporting asymmetry. An off-directory `-game` smoke-test file also failed because the runner could not find the game's bundled Chinese font. A temporary sidecar beside the installed data worked and allowed the installed file hash to remain intact.

## Resume here

Run the updated [guest ship playtest](README.md#guest-ship-playtest) on two protocol 4 PCs. Confirm that a guest can redirect the crew between two vacant tiles in the same room, that the host's occupied-tile fallback matches native precision behavior, and that the guest highlights the host's final tile. The guest fixture used synthetic inputs and snapshots. If the click path fails, use the numbered panel to isolate the host room-order path.

The long-term target is a guest experience with native presentation and controls. The current custom view and numbered panel are test interfaces. The networking goal is to send the combat state the guest needs without periodic full-game snapshots. One candidate is host-authoritative combat with guest-side crew prediction corrected by host state. The current guest renders a limited snapshot view and runs no local combat simulation. Whole-game rollback feasibility is unverified. A seed alone cannot reconcile different RNG call orders. Whole-game rollback would require deterministic frame replay and reliable state capture and restore.
