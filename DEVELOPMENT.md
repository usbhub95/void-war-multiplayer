# Development handoff

## Goal and scope

Build remote co-op for two players sharing control of one ship in Void War. The long-term requirement is for the guest to issue crew orders through the same native interaction used in single-player.

The current target is the full Windows Steam game, build `26906873`, with a copy of the game on each PC. Steam networking was the first choice. Direct IP was the agreed fallback if Steam failed the remote connection test. That test passed, so the project uses Steam. Keep original game data, patched binaries, and extracted game assets out of Git. Build and install from each player's own copy using the [README](README.md#build).

## Current checkpoint

The occupied-tile guest order fix passed its two-PC playtest. The next feasibility test is the [proposed native guest selection experiment](#proposed-native-guest-selection-experiment).

## Architecture and game integration

- [New-Build.ps1](New-Build.ps1) verifies the installed vanilla data and generates `build/data.win`. See the [README](README.md#build) for build, launch, and cleanup commands. [VoidWarMultiplayer.csx](src/VoidWarMultiplayer.csx) compiles the GML, registers two Steam extension functions the compiler otherwise treats as variables, and installs a guarded creation hook in `rmMainMenu`. The persistent probe is intended to carry the connection through room changes without spawning a duplicate on return to the menu.
- [Create.gml](src/Create.gml) and [Step.gml](src/Step.gml) handle Steam IDs, the in-game editor, and the two-peer session. IDs are parsed digit by digit as 64-bit integers. The peer's Steam ID, packet bounds, magic, game build, and protocol version are checked. Ping/pong measures RTT and detects loss of replies. **F10** closes the local session. [Cleanup.gml](src/Cleanup.gml) also frees the buffers when the probe is destroyed.
- [CrewTest.gml](src/CrewTest.gml) uses probe protocol **5**. The 15-byte header still carries magic, build, protocol, packet kind, and sequence. Per-share layout packets carry room bounds, native tile positions, and sprite names. The host retries layout until the guest acknowledges that share generation. Separate updates every 250 ms carry the crew position, target tile, arrival, order acknowledgement, and native sprite pose. Each update is 42 bytes plus the sprite name, capped at 64 bytes. The pinned runner resolved asset names but returned `-1` when the fixture passed a sprite handle to `asset_get_index`. The guest retries its pending numbered order until a snapshot acknowledges it or a newer click replaces it. The host uses the sharing token to reject orders for an old selection and sequence numbers to avoid applying duplicates. Room numbers refer to cells in the host's map of up to 24 rooms. GameMaker instance IDs stay on the host.
- The native room-click path in `oCell` Step calls `crew_move_set_target` from `scrCrewMovement` for ordinary room movement. The host uses the underlying native room-slot chooser for guest room orders after checking the live crew, hull, and destination. `currentCellID` is the reserved destination and can change before physical arrival. The snapshot uses `collidingCellID` while moving and `crew_has_reached_destination` to report arrival. The host runs the encounter. The last valid order processed by the host wins, whether it came from the host or the guest. The playtest confirmed this behavior and the user approved it. The numbered guest panel remains available at the title screen. The optional guest ship view uses the same ordered room slots and sends orders to the same host handler.
- [GuestView.gml](src/GuestView.gml) draws the local hull and native crew sprite from host-supplied layout and crew pose, with the portrait as a fallback. The guest interpolates position locally using the latest host samples and advances the animation from the host frame at the reported rate. Drawing and click selection share the same interpolated position. The new guest room is outside the normal room order and contains no combat instances. The guest selects the crew marker with a left-click and right-clicks the nearest native tile within a room. The host validates the tile and uses the native movement and reservation helpers for vacant and occupied tiles. The numbered panel still sends ordinary room orders. Both clicks use the same coordinate transform as drawing.

References for build-specific work include the [Void War developer FAQ](https://steamcommunity.com/app/2853590/discussions/0/4695658570140629717/), [UndertaleModTool 0.9.2.0](https://github.com/UnderminersTeam/UndertaleModTool/releases/tag/0.9.2.0), [GameMaker instance persistence](https://manual.gamemaker.io/lts/en/GameMaker_Language/GML_Reference/Asset_Management/Instances/Instance_Variables/persistent.htm), and [Valve's legacy P2P API reference](https://partner.steamgames.com/doc/api/ISteamNetworking). Valve deprecates that API. It is the one available through Void War's bundled GameMaker extension and used in the successful connection playtest.

## Technical history and known issues

- `b3efb45` fixed the old native dialog crash. UndertaleModTool compiled `async_load[? "id"]` as array indexing and tried to convert `"id"` to an integer. Explicit map lookups worked in the runner. `5bb993f` then removed the native dialog because returning from Alt-Tab in fullscreen made it minimize whenever the player interacted with it. The in-game editor keeps its own draft across focus changes.
- `8b484ba` fixed a receive crash caused by `steam_net_packet_get_size` compiling as a variable read. `steam_net_close_p2p_session` had the same problem. Register both using their bundled extension declarations before compiling and verify direct calls. Both ran in Steam.
- With a mismatched version, the peer that detects the mismatch closes the session immediately. Two-PC testers saw a mismatch on one side and **No reply** on the other.
- An off-directory `-game` smoke test failed when the runner could not find the bundled Chinese font. Launching a sidecar beside the installed data resolved it and preserved the installed file hash.

## Implementation notes

### Guest animation

The first [protocol 5 guest ship playtest](README.md#guest-ship-playtest) worked overall, with guest animation jitter reported. In the later Empire cruiser playtest, the user reported that animations looked normal with the game focused and suspected a background application frame limiter. Each accepted crew update also resets the guest to the host's animation frame. A synthetic timing example showed that uneven arrivals can rewind or skip frames. The earlier jitter's cause remains unverified. Animation tuning is deferred.

### Native input experiment

Inspection of the pinned build found that the native right-click branch in `oCell` Step uses the selection in `oUICursor.currSelected` and checks live hull, room, and crew state. It chooses ordinary room movement, a vacant precision tile, or the occupied-tile fallback. An ordinary click in the same room can also target a system console. The same Step event handles oxygen and hazards, so reusing the whole event in the guest's empty room would also bring in simulation dependencies.

The optional [diagnostic patch](src/NativeCrewInput.csx) redirects the four right-click movement calls to observers. Each observer logs the single-crew intent and forwards the original arguments. UndertaleModTool reopened the build and confirmed that the rest of the room Step event disassembled identically, including a later simulation-driven movement call. The original diagnostic used the earlier protocol 5 probe. Two builds matched SHA-256 `BD486434187FD7F5D16D2978D507D08B127F04FD793AD953B3680EFB19295958`. The Steam runner emitted the diagnostic startup marker from the sidecar. The installed game data hash matched before and after the smoke test. The current `-NativeInput` build uses installed vanilla data. Two builds matched SHA-256 `1E372F661CA3B98A185D068DEEB3D2A54D5D00C20D89939945FDC1EB2F822658`. The rebuilt diagnostic reopened with all four native call targets.

The one-PC [native crew input playtest](README.md#native-crew-input-experiment) on 27 November 2026 recorded five orders for the same crew member in this sequence. Room move, vacant precision slot 3, occupied precision slot 2, vacant precision slot 3, and same-room console slot 2. The user reported ending with about four no-selection clicks. No order followed the console entry before normal shutdown, consistent with those clicks being ignored. The user confirmed that the crew behaved as expected in gameplay. The trace establishes a place to capture these four native movement intents for a future guest view.

### Empire cruiser guest scene

The optional **F4** mode in the guest room uses the bundled hull, border, and room sprites for **Triumph of Heaven** (`rmStart_EMCruiserA_gunBoarding`). The normal hull and cell Draw events depend on live run state and perform effects, visibility, and hover updates. The guest draws the sprites directly. [VoidWarMultiplayer.csx](src/VoidWarMultiplayer.csx) reads the 20 placed cells from the pinned starter room. [NativeGuestShip.gml](src/NativeGuestShip.gml) checks the hull and matches each received room by normalized position, dimensions, and numbered tile centers. The existing layout view is the fallback for a mismatch. Protocol 5 supplies the layout, hull pose, and crew pose. Both views use the same guest click handler.

Two builds from pinned vanilla matched SHA-256 `18DA6C00022F4365D7983D96BFCA7196DEF61C23FC47E5A81795FF98EBD0838E` for the original cruiser presentation build. UndertaleModTool reopened the build and confirmed direct sprite calls, an empty guest room, and identical disassembly for the inspected native hull, cell, cursor, and room initialization code. A temporary Steam fixture matched all 20 room origins in reversed room order, rejected mismatched bounds, tiles, duplicates, hull and orientation, and decoded synthetic layout and crew packets. It entered the guest room, ran both draw paths, checked click-to-tile mapping, cleared the match on a new share, and returned to the title screen. The installed `data.win` matched its pre-test hash.

The user confirmed that the two-PC [Empire cruiser guest view playtest](README.md#empire-cruiser-guest-view-playtest) displayed the hull, border, and rooms correctly. The guest scene contains the shared crew member. The user also observed the expected absence of walls, doors, and other crew.

### Host handling of guest orders

The pinned game's occupied-tile helper reads the local mouse, precision setting, and selection. Its ordinary room-move wrapper can call the same helper. Guest room orders now call the underlying native room-slot chooser. For an occupied tile, the host looks up the occupant at the requested slot, checks the game's displacement conditions, and reserves the slot with the native helpers. It restores both reservations if the displaced crew member cannot be reassigned. The host acknowledges a tile order by checking that the crew has reserved that exact tile.

Two builds from pinned vanilla matched SHA-256 `5704E490CF5530F29188BB9146C6416B545AE47B8A9CB1C01EF201DACC119415` for the co-op build at `0ea809d`. The consolidated build script later reproduced that hash in `build/data.win`. UndertaleModTool verified direct compiled calls to the native helpers and identical disassembly for the native room Step and movement scripts. The actual host-order GML passed a local harness with simulated movement helpers for ordinary, vacant, occupied, blocked, stale, duplicate, and rollback cases. The user confirmed in a live [occupied-tile playtest](README.md#guest-ship-playtest) that a guest order moved the shared crew into the occupied tile and the allied occupant moved aside as in vanilla.

### Proposed native guest selection experiment

In normal single-player, `oUICursor` Draw GUI End calls `scrCursorCrewSelection`. It reads mouse release and drag coordinates, uses the `oCrew` selection collision instances, and writes the cursor's selection list. The next feasibility test is to run that routine for one mirrored crew member in the isolated guest room. Check whether lightweight local objects can supply the cursor list and crew collision shape, with the combat events isolated. Compare click, drag selection, and clearing selection against the native game. Verify that the existing guest tile-order handler consumes the result. The native right-click branch depends on additional live room and crew state.

## Long-term direction

The long-term target is a guest experience with native presentation and controls. The current custom view and numbered panel are test interfaces. The networking goal is to send the combat state the guest needs without periodic full-game snapshots. One candidate is host-authoritative combat with guest-side crew prediction corrected by host state. The current guest renders a limited snapshot view and runs no local combat simulation. Whole-game rollback feasibility is unverified. A seed alone cannot reconcile different RNG call orders. Whole-game rollback would require deterministic frame replay and reliable state capture and restore.
